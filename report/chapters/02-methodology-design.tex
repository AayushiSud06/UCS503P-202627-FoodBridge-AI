\chapter{Methodology and Design}
\label{ch:methodology}

FoodLink was built incrementally, in the iterative style the proposal
committed to~\cite{foodlinkProposal,sommerville2016}. Work was organised as
numbered tasks, the most recent being Task~46. Each task was small enough to
review on its own and carried its own regression tests. Every
non-trivial technical choice was recorded with its reasoning and constraints
in a decision log. That log currently holds entries D-01 to D-61, and
this chapter cites entries by number where they explain a design
choice~\cite{foodlinkArchitecture}. Three audits were run against the working
system: a quality audit on 2 September 2026, and health audits on 5 and 10
September 2026. Their findings were prioritised from P0 (stop everything) to
P3 (backlog) and fixed in that order. The five P1 findings of the latest audit
are all fixed (Section~\ref{sec:analysis}). Continuous integration runs the
complete backend and frontend test suites on every push.

\section{System Architecture}
\label{sec:architecture}

\subsection{High-Level Design}
\label{sec:hld}

FoodLink follows a classic three-tier architecture, shown in
Table~\ref{tab:layers}. The \emph{presentation tier} is a React single-page
application running in the browser. The \emph{application tier} is a stateless
REST API implemented with FastAPI and served by uvicorn. The \emph{data tier}
is a relational database reached only through the SQLAlchemy object-relational
mapper; no hand-written SQL appears in the application code.

\paragraph{Backend layering.} Inside the API, dependencies point one way:
\emph{routers} call \emph{shared pure modules}, and both use the \emph{ORM}.
The five routers are \code{auth}, \code{donations}, \code{organisations},
\code{admin} and \code{metrics}. The shared modules are \code{matching},
\code{serialize}, \code{security} and \code{ratelimit}. The project
deliberately has no separate service or repository layer (D-07). Logic that is
genuinely reusable and independent of HTTP (the ranking arithmetic, the
serializer that applies disclosure rules, token handling and rate limiting)
was extracted into modules, while request orchestration stays in the router
functions. The matcher in particular holds no database session, which is why
it can be unit-tested directly.

\paragraph{Read path.} When a signed-in user opens a page, the frontend's
single HTTP client (\code{lib/api.ts}) attaches the stored bearer token and
calls, for example, \code{GET /api/donations}. FastAPI resolves the dependency
chain before the handler runs:
\begin{enumerate*}[label=(\roman*)]
  \item \code{get_db} opens a database session;
  \item \code{get_current_user} verifies the token's signature and expiry,
    then re-reads the user row, refusing a deleted or suspended account;
  \item where a route is role-restricted, \code{require_roles} checks the role
    held in that row.
\end{enumerate*}
The handler then asks a scope helper (\code{_readable_by}) for a SQL
\code{WHERE} clause describing exactly which donations this caller may read,
and applies it inside the query. Related rows are loaded with
\code{selectinload}, so a page of donations costs a fixed number of queries
rather than one per row. Finally \code{serialize.donation_out} converts each
row into the camelCase JSON shape, withholding any field the caller's
relationship to the donation does not justify. The frontend's
\code{lib/adapters.ts} translates that JSON into the domain types the
components render.

\paragraph{Write path.} A button such as \emph{Accept} calls a mutation in
\code{AppContext}, which posts to the API. The handler validates the body
against a Pydantic schema. It then checks, in order, the lifecycle transition
table, the caller's role, the caller's ownership of the donation and any
target-specific rules. It applies side effects, performs a
\emph{conditional} status write, appends a \code{StatusEvent}, and commits
everything in a single transaction. The client then reloads its data from the
server rather than patching its local copy (D-11), so the browser can never
disagree with the server about the lifecycle state.

\paragraph{External dependencies and background work.} The backend makes no
outbound network requests. It has no email, SMS, push, map, payment or
object-storage integration, and no scheduler, queue or worker process. In
development, Vite's server proxies \code{/api} to the backend on port 8000, so
the browser talks to a single origin. In any other arrangement, a CORS
allowlist (by default \code{http://localhost:5173} and
\code{http://127.0.0.1:5173}) decides which origins the browser may call from.

\subsection{System Requirements}
\label{sec:sysreq}

\paragraph{Software requirements.} To run FoodLink locally:
\begin{itemize}
  \item Python 3.10 or later (3.13 is used in development and CI), with the
    packages in \code{code/requirements.txt};
  \item Node.js with npm (CI uses Node.js 20), with the packages in
    \code{frontend/package.json};
  \item no separate database server, since SQLite is used by default and the
    schema is migrated automatically when the API starts;
  \item a signing key in \code{FOODLINK_SECRET_KEY} (at least 32 characters).
    For local development only, \code{FOODLINK_DEV_INSECURE_SECRET=1} selects a
    known development key and makes the server print a warning. Without one of
    the two, the backend, the command-line tool and Alembic all refuse to start
    (D-22);
  \item a current web browser for the portals.
\end{itemize}

\paragraph{Hardware requirements.} The repository defines no minimum hardware
specification, and none has been measured. The system has so far been
developed and tested on ordinary developer laptops and on GitHub-hosted
Ubuntu CI runners. Constraints relevant to future hosting are discussed in the
Feasibility Report (Section~\ref{sec:feas-technical}).

Several design choices shape this schema.
\begin{itemize}
  \item \textbf{Single user table, satellite profiles.} Roles are an enumerated
    column, not a class hierarchy. Registering as an organisation creates a
    \code{recipients} row, and registering as a courier creates a
    \code{volunteers} row, so each account is ready to act immediately.
  \item \textbf{Events instead of timestamp columns (D-01).} A column such as
    \code{accepted_at} could record neither who acted nor a state entered twice
    (a released pickup re-enters \code{ACCEPTED}). The ledger records both,
    and adding a state needs no migration. \code{occurred_at} is never
    accepted from a client, which is what makes the metrics attributable.
  \item \textbf{Derived values stay derived (D-15).} An organisation's
    reliability score is a computed property. It is 85 until the organisation
    has three accepted donations, then $100 \times \text{completed} /
    \text{accepted}$. Distance is computed from two coordinate pairs, never
    stored. The one deliberate exception is \code{match_score}, frozen so
    that the number shown later is the one a decision was actually made on
    (D-30).
  \item \textbf{Counters maintained by the lifecycle.} The acceptance and
    completion counters are updated inside the same transaction as the
    transition that justifies them. A cancellation takes a counted acceptance
    back out (D-58), so a donor's or administrator's cancellation never lowers
    an organisation's reliability.
  \item \textbf{Time zones.} A custom column type, \code{UtcDateTime},
    normalises every timestamp to timezone-aware UTC on write and re-attaches
    UTC on read. SQLite has no timezone type, and a zoneless deadline would
    otherwise be read by browsers as local time (D-09).
  \item \textbf{Invariants in application code.} The state machine, coordinate
    ranges and counters are enforced by the application, not by database
    constraints, and SQLite does not enforce foreign keys by default. The
    lifecycle's own writes nevertheless carry their preconditions in SQL
    (Section~\ref{sec:module-lifecycle}).
\end{itemize}

\paragraph{Conventions.} The API answers consistently, and the frontend relies
on that consistency.
\begin{itemize}
  \item \textbf{Errors are sentences.} Every refusal carries a human-readable
    \code{detail}, which the frontend shows verbatim (D-18). Sign-in uses one
    message for both an unknown email and a wrong password, so the response
    does not reveal which addresses have accounts.
  \item \textbf{Status codes carry meaning.} 401 means the token is invalid or
    the account is unusable. 403 means the role or trust level is
    insufficient. 404 means not found \emph{or not visible to you}. 409 means
    the donation is not in a state that allows the request. 422 means the
    input is invalid. 429 means a rate limit was hit, and carries a
    \code{Retry-After} header.
  \item \textbf{Denial never confirms existence.} A donation outside the
    caller's scope returns the same 404 as one that does not exist (D-24), and
    a directory the caller may not read returns an empty list (D-26).
  \item \textbf{PATCH has three states per field (D-61).} An omitted field is
    untouched. An explicit \code{null} clears a nullable column, such as a pin
    or phone number, and leaves a mandatory column unchanged rather than
    causing a server error.
  \item \textbf{Privileged fields are absent from self-service schemas (D-16).}
    For example, \code{RecipientUpdate} has no \code{is_verified} field, and
    \code{ProfileUpdate} has no \code{role}.
\end{itemize}

\paragraph{Backend modules.} \code{main.py} creates the application, installs
CORS and the routers, and runs \code{ensure_schema_current()} at start-up,
which applies any outstanding Alembic revision. A database that predates
migrations is reported rather than rewritten (D-23). \code{config.py} reads
settings from the environment; the most important is the fail-closed signing
key. \code{cli.py} provides \code{create-admin}, \code{promote},
\code{reset-password} and \code{list-admins}. The first administrator can only
be created this way, because the API has no route to one (D-04). \code{seed.py}
loads demonstration data.

\subsection{Frontend Architecture}
\label{sec:frontend}

The web client is a React single-page application with a small, deliberate
set of seams.
\begin{itemize}
  \item \textbf{One HTTP boundary (D-12).} \code{lib/api.ts} is the only module
    that calls \code{fetch}. It attaches the token, turns error responses into
    an \code{ApiError} carrying the server's sentence, and signals a 401 to the
    whole application at once. \code{lib/adapters.ts} maps wire types to the
    domain types the components use.
  \item \textbf{Two context providers.} \code{AuthContext} keeps the token in
    \code{localStorage} and re-fetches the account from \code{/api/auth/me} on
    start-up, so a suspended or re-roled account cannot act on a stale copy of
    its own permissions (D-13). \code{AppContext} loads the donation list (up to
    500 rows) and the role-appropriate slices (requirements, organisations,
    couriers, metrics) once per sign-in. It reloads them after every write
    (D-11). A \code{useAction} hook tracks in-flight state and shows success or
    error toasts.
  \item \textbf{Routing and guards.} React Router mounts four portals:
    \code{/donor}, \code{/ngo}, \code{/volunteer} and \code{/admin}.
    Each sits behind a \code{ProtectedRoute} that redirects users away from
    portals their role does not use; administrators may enter every portal.
    These guards are a user-experience convenience, not security. The API
    independently refuses anything the role may not do (D-14).
  \item \textbf{Utilities.} \code{lib/geo.ts} chooses which distance or
    location text to display, including the coarse pickup area shown to
    couriers. \code{lib/time.ts} computes urgency from the absolute deadline.
    \code{lib/impact.ts} computes each account's own impact figures from its
    own donations (D-32). \code{lib/image.ts} decodes a chosen photo, scales its
    long edge to at most 1280\,px and re-encodes it as JPEG at decreasing
    quality until it fits the server's 256\,KiB cap (D-56).
  \item \textbf{Styling.} Tailwind CSS with a customised warm palette and
    typefaces (D-10), and lucide-react icons.
  \item \textbf{Phone layouts.} A parallel set of phone-layout screens under
    \code{src/mobile/} is mounted at \code{/m/*}. Nothing links to them yet, so they are reached by
    typing the address (D-20).
\end{itemize}

\section{Implementation Details}
\label{sec:implementation}

This section documents the implementation module by module. Modules~1 to~3
form the core functionality: the lifecycle, the matching and the access
model. Modules~4 to~6 are the secondary features built on them.

\subsection{Module 1: Core Functionality --- Donation Lifecycle}
\label{sec:module-lifecycle}

The donation lifecycle is the core of FoodLink. It lives in
\code{routers/donations.py}, with the state graph in \code{models.py}. It has
nine states (Table~\ref{tab:states}) and is governed by two tables that are
plain data rather than scattered conditionals (D-02).
\code{ALLOWED_TRANSITIONS} says which moves are legal at all; any other move is
answered with 409. \code{TRANSITION_ROLES} says which roles may cause each target
state; any other role is answered with 403.

\code{ALLOWED_TRANSITIONS} also permits \code{MATCHED} $\to$ \code{AVAILABLE},
but no role is listed for it, so it cannot currently be performed.

\subsubsection{Donation creation}
\code{POST /api/donations} is open to donors and administrators. Before the
handler runs, a dependency applies two sliding-window rate limits to donors:
10 posts per hour per account and 30 per hour per client address, each with
its own 429 sentence. Administrators are exempt (D-59). The Pydantic schema
bounds every field to its column size. Free text such as the description is
capped at 2{,}000 characters (D-60). The quantity must be positive, the
coordinates must be valid, and \code{imageUrl} must be either a base64 image
data URL of at most 262{,}144 characters or an \code{http(s)} link (D-56). The
handler then refuses a deadline that is not in the future, stores the donation
as \code{AVAILABLE} and appends the first event. It loads every recipient
organisation with its active requirements, ranks them
(Section~\ref{sec:module-matching}), and if any is eligible freezes the
leading score and records \code{MATCHED} with the note ``Top match: \emph{name}''.
Everything commits once, and the response is serialized under the caller's
scopes.

\subsubsection{The transition algorithm}
Every other transition goes through one endpoint,
\code{POST /api/donations/{id}/status}, whose handler \code{update_status} applies
the checks in a fixed order:
\begin{enumerate}
  \item load the donation (404 if the id does not exist);
  \item refuse a move absent from \code{ALLOWED_TRANSITIONS} (409);
  \item refuse a caller whose role is not in \code{TRANSITION_ROLES} for the
    target (403);
  \item for \emph{owned} transitions (\code{PICKED_UP}, \code{DELIVERED},
    \code{COMPLETED}, \code{CANCELLED}, and \code{ACCEPTED} when it is a
    release), re-load the donation through the caller's own read scope. A
    caller who is not this donation's donor, courier or accepting organisation
    therefore receives the same 404 a read would give (D-34, D-35);
  \item apply the target-specific rules and side effects described in
    Table~\ref{tab:transitions};
  \item perform the conditional status write and append the event, or refuse
    with 409;
  \item for a cancellation, withdraw the counted acceptance;
  \item commit once and return the donation as the caller is allowed to see it.
\end{enumerate}

\subsubsection{Concurrency: conditional writes}
A lifecycle system that reads a row, checks it in Python and then writes it is
vulnerable to \emph{lost updates}. Two organisations can both read
\code{AVAILABLE}, both conclude they may accept, and both succeed, which
really happened before this was fixed~\cite{kleppmann2017}. FoodLink closes
this by making the check and the write the same database statement. The
helper \code{_record} advances the status with
\begin{center}
\code{UPDATE donations SET status = :to WHERE id = :id AND status = :from}
\end{center}
and treats a row count other than one as a conflict. It returns 409 with the
state the row is now in, and appends no event. Because the write runs last
before the single commit, a refused transition also rolls back its side
effects, such as a counter increment or a frozen score (D-55). The courier
claim uses a second conditional statement. It sets \code{volunteer_id} only
if the status is still the expected one and the pickup is unclaimed (or
already this courier's), so exactly one of several simultaneous claims wins
(D-28). The alternative, \code{SELECT ... FOR UPDATE}, was rejected because
SQLite silently ignores it. The fix would then have been untestable on the
engine the project uses.

\subsubsection{Acceptance, claim and release}
An organisation always accepts as itself. If it names another organisation's
id, it receives 403. Only an administrator may accept on an organisation's
behalf. Verification is re-checked at acceptance, so an unverified
organisation cannot take custody even if it obtains a donation's id (D-06). An
overdue donation in the open pool cannot be accepted (409). This keeps
behaviour identical whether or not the expiry sweep has run (D-50).
Acceptance from \code{VOLUNTEER_ASSIGNED} is a \emph{release}, not an
acceptance: the courier is removed so that other couriers can claim the pickup,
and neither the acceptance counter nor the frozen score changes (D-41). In
the current web portal there is no release control; it is available through
the API.

\subsubsection{Cancellation and expiry}
A donor may cancel their own donation in \code{AVAILABLE}, \code{MATCHED},
\code{ACCEPTED} or \code{VOLUNTEER_ASSIGNED}. Once the food is in a courier's
hands (\code{PICKED_UP}), only an administrator may cancel. If an organisation
was bound, the cancellation decrements its acceptance counter with a single
conditional SQL statement floored at zero. As a result, a cancellation it
did not cause cannot lower its reliability score (D-58). The expiry sweep
(\code{POST /api/admin/maintenance/expire}) closes every \code{AVAILABLE} or
\code{MATCHED} donation whose deadline has passed. It appends an event with no
actor and the note ``Deadline passed with no recipient'', and returns the
number expired. Nothing schedules it; an administrator triggers it from the
donations page.

\subsubsection{The event ledger and metrics}
Each \code{StatusEvent} records the previous and new state, the acting user,
an optional note (bounded to 2{,}000 characters) and a server timestamp. The
donation detail screens render these rows as a timeline. \code{GET
/api/metrics} computes the proposal's evaluation figures from the same rows
(Section~\ref{sec:module-admin}).

\subsection{Module 2: Core Functionality --- Recipient Matching and Explainability}
\label{sec:module-matching}

\code{matching.py} ranks recipient organisations for a donation. It is a
transparent weighted-sum heuristic and deliberately \emph{not} a learned
model: the proposal committed to an explainable ranking that a recipient can
read and a marker can verify by hand (D-05). The module is pure Python with
no database access; the routers load the rows and pass them in.

\subsubsection{Eligibility gates}
Before any score is computed, \code{score_pair} excludes an organisation
entirely (returns nothing) if any of three gates fails (D-06):
\begin{enumerate*}[label=(\roman*)]
  \item it is not verified by an administrator;
  \item it has no map coordinates;
  \item its great-circle distance from the pickup pin exceeds the service
    radius $R$, which is 8\,km by default (\code{MAX_MATCH_RADIUS_KM}).
\end{enumerate*}
Gating rather than scoring low is intentional. A suggestion the organisation
is not allowed to act on would be a false promise to the donor.

\subsubsection{Scoring criteria}
Let $d$ be the haversine distance in kilometres between the pickup pin and
the organisation~\cite{sinnott1984haversine}, $q$ the donation's quantity,
$c$ the organisation's capacity in meals, $a$ and $k$ its accepted and
completed donation counts, and $m$ the minutes remaining until the pickup
deadline. Each criterion yields an integer from 0 to 100 (``round'' denotes
Python's \code{round}, which sends exact halves to the nearest even integer).

\emph{Distance} decays linearly to zero at the radius:
\begin{equation}
  S_D = \begin{cases} \operatorname{round}\!\left(100\left(1 - d/R\right)\right) & d < R\\ 0 & d \geq R \end{cases}
\end{equation}

\emph{Quantity fit} is assessed only when the donation's unit is ``Meals'',
because capacity is counted in meals and the repository holds no conversion
rule (D-42). With $r = q/c$, overfilling is penalised twice as steeply as
underfilling:
\begin{equation}
  S_Q = \begin{cases} \operatorname{round}(40 + 60r) & r \leq 1\\ \max\left(0, \operatorname{round}(100 - 120(r-1))\right) & r > 1 \end{cases}
\end{equation}

\emph{Capacity headroom} measures how much room the organisation keeps
afterwards, in absolute meals, saturating at 100 spare meals:
\begin{equation}
  S_C = \begin{cases} \operatorname{round}\!\left(100 \min\left(1, (c-q)/100\right)\right) & c - q > 0\\ 0 & c - q \leq 0 \end{cases}
\end{equation}
For any other unit (Kg, Boxes, Pieces), $S_Q = S_C = 50$, which is identical for
every candidate and so cannot reorder them, and the explanation says the size
was not assessed.

\emph{Deadline comfort} subtracts a rough travel estimate
$t = 60d/20$ minutes (a flat 20\,km/h, never shown to users as an arrival time)
and treats two hours of slack as fully comfortable:
\begin{equation}
  S_T = \begin{cases} \operatorname{round}\!\left(100\min\left(1, (m - t)/120\right)\right) & m - t > 0\\ 0 & m - t \leq 0 \end{cases}
\end{equation}

\emph{Reliability} starts optimistic so that a new organisation is not
permanently outranked by one with a single lucky completion:
\begin{equation}
  S_R = \begin{cases} 85 & a < 3\\ \operatorname{round}(100k/a) & a \geq 3 \end{cases}
\end{equation}

The overall score is the weighted sum, with the weights published in the
\code{WEIGHTS} constant (Table~\ref{tab:weights}):
\begin{equation}
  S = \operatorname{round}\left(0.25\,S_D + 0.25\,S_Q + 0.20\,S_C + 0.15\,S_T + 0.15\,S_R\right)
  \label{eq:overall}
\end{equation}

\subsubsection{Ordering and the role of requirements}
Candidates are sorted by a total order: overall score first, then a
\emph{requirement tier}, then requirement fit, then the urgency of that
requirement, and finally the organisation id. An organisation's active
standing requirements therefore break ties but never change a score (D-52).
The best requirement for a donation is the one whose unit matches the
donation's unit (no conversion) with the highest fit, where fit is 100 when
the donation covers the stated quantity $n$ and $\operatorname{round}(40 + 60q/n)$
otherwise. A kitchen whose need can be measured ranks above one whose need
cannot, which ranks above one with no posted need. Requirements are kept out of
the score because the frozen \code{match_score} is visible to readers who may
not read requirements. A score derived from them would leak private demand.

\subsubsection{Two scores and location privacy}
A donation carries two different figures that must not be confused (D-30).
\code{matchScore} is \emph{frozen}. It is written at posting (the top
candidate's score) and replaced at the first acceptance by the accepting
organisation's own score. \code{viewerMatch} is \emph{live}. It is the reading
organisation's own ranking, computed on each request while the donation is
still open, and it is what the organisation's \emph{Available Donations} screen
shows with its breakdown. Location-derived figures are restricted because
scores and distances read back from pins of a donor's choosing could otherwise
be used to triangulate an organisation's private address (D-45, D-47). When
anyone other than the organisation itself (or an administrator) reads a
ranking, the organisation's coordinates are first snapped to a 0.01$^\circ$ grid
(roughly one kilometre), and \code{distanceKm} is returned as null. The frozen
\code{matchScore} and \code{distanceKm} on a donation are visible only to
administrators and to the organisation the figure describes. Eligibility
itself is always decided on the true position, so the set of ranked
organisations never depends on who is asking.

\subsubsection{Design for future replacement}
The router and the response shape depend only on \code{score_pair} and
\code{rank_recipients}. If outcome data later justified a learned ranker, it
could replace \code{score_pair} without changing the rest of the system. That
is a design property, not an implemented capability.

\subsection{Module 3: Core Functionality --- Authentication, Authorization and Trust}
\label{sec:module-auth}

\subsubsection{Accounts and authentication}
Registration (\code{POST /api/auth/register}) accepts a name, an email, a
password of 8 to 128 characters and a role. The schema itself refuses the
\code{admin} role, so the restriction is visible in the published API
documentation (D-04). Registering as an organisation creates an
\emph{unverified} recipient row, optionally with type, address, coordinates
and capacity. Registering as a courier creates a courier row. Passwords are
stored as bcrypt hashes~\cite{provos1999bcrypt}. Sign-in uses the OAuth~2.0
password form, with the email in the \code{username} field~\cite{rfc6749}. It
returns a JSON Web Token signed with HMAC-SHA256~\cite{rfc7519}, carrying the
user id, role and an expiry 720 minutes ahead. The browser keeps the token in
\code{localStorage} and sends it as a bearer header. On every request,
\code{get_current_user} verifies the token and \emph{re-reads the user row},
ignoring the role claim. A suspension or role change therefore takes effect on
the very next request (D-03). There is no refresh token, revocation list or
multi-factor authentication. The signing key must be configured and at least
32 characters long; the service will not start with a missing or known-public
key (D-22).

\subsubsection{Administrators}
The first administrator can only be created from the command line
(\texttt{python -m foodlink.cli create-admin}), because the API offers no
anonymous path to that role. Later administrators are created by an existing
administrator through \code{POST /api/admin/users}. Two lockout guards
refuse an administrator suspending or demoting their own account, and refuse
suspending or demoting the last active administrator.

\subsubsection{Four layers of authorization}
Every operation passes through up to four independent checks:
\begin{enumerate}
  \item \textbf{Role}: \code{require_roles} or \code{TRANSITION_ROLES} (403).
  \item \textbf{Ownership}: expressed as a SQL \code{WHERE} clause returned by a
    scope helper, so the database never returns rows the caller may not see
    (404 or an empty list).
  \item \textbf{Lifecycle legality}: \code{ALLOWED_TRANSITIONS}, the donor
    cancellation window and the deadline rule (409).
  \item \textbf{Trust}: \code{Recipient.is_verified}, set only by an
    administrator, and read by ranking, acceptance and the organisation's
    access to the open pool (D-37, D-53).
\end{enumerate}

Table~\ref{tab:scopes} lists the read scopes as implemented. Besides deciding
\emph{which} records a caller receives, FoodLink decides \emph{what} a record
says to that caller. An unclaimed pickup in a courier's queue carries a
coarse \code{pickupArea} (the donor's pin snapped to the 0.01$^\circ$ grid)
instead of the exact coordinates, address text and donor name. Claiming the run
is what discloses them (D-57).

\subsubsection{Verification as a trust boundary}
Organisations begin unverified, except when an administrator creates the
account, which counts as vouching for it. An unverified organisation is not
ranked, cannot see the open pool and cannot accept. Its own donations remain
readable to it. Verification is read live on every request, so revoking it
closes the pool at once. Because verification vouches for \emph{who} and
\emph{where} an organisation is, a real change to its name, latitude or
longitude through \code{PATCH /api/recipients/me} clears the flag in the same
commit, and an administrator must verify it again (D-54). Resubmitting unchanged
values, or editing type, address text, capacity or contact details, does not
affect it.

\subsubsection{Abuse limits and input bounds}
Anonymous routes are limited per client address (30 sign-in attempts per 5
minutes; 10 registrations per hour). Donation posting is limited per donor
account and per address (Section~\ref{sec:module-lifecycle}). All limits are
sliding windows held in the server process's memory (D-27, D-59). Request
schemas bound every donation and requirement text field to its column size,
bound free text to 2{,}000 characters, and bound photos to 256\,KiB of data URL.
Account and organisation profile text fields are not yet bounded.

\subsection{Module 4: Secondary Features --- Standing Requirements}
\label{sec:module-requirements}

Standing requirements make demand visible before surplus appears. An
organisation posts a need with a food type, quantity and unit, beneficiary
count, an urgency label (the ranking recognises High, Medium and Low), a
daily-recurring flag and notes
(\code{POST /api/requirements}). The whole lifecycle is one flag,
\code{is_active}, changed through \code{PATCH /api/requirements/{id}} (D-29).
Setting it false retires a need, whether it was met or no longer applies. The
row is kept, and setting the flag true reopens it. Ownership is part of the
query, so another organisation's requirement id returns 404. Reads are scoped
(D-44, D-46): donors see the active needs of verified organisations on the
\emph{Needs Board}; an organisation sees its own, including retired ones when
it asks with \code{includeInactive}; couriers see none. In ranking, an active
requirement only breaks ties and adds a reason
(Section~\ref{sec:module-matching}). Food type, beneficiary count, recurrence
and notes are not ranking inputs.

\subsection{Module 5: Secondary Features --- Administration and Platform Metrics}
\label{sec:module-admin}

The administration router is protected by a single role dependency declared
once for all of its routes. Through the web portal, an administrator can
verify or revoke organisations (\emph{Partner Organizations Directory}), browse and filter
every donation, export the filtered list as CSV, and trigger the expiry sweep
(\emph{Platform Donation Ledger}). The administrator can also view the courier roster
and the analytics dashboard. Account management (listing, creating,
suspending, restoring and re-roling users) is implemented and tested in the API
but has no screen yet. Because every entry in \code{TRANSITION_ROLES} includes
the administrator, an administrator can also perform lifecycle transitions on
a party's behalf, subject to the same legality rules.

\code{GET /api/metrics} loads every donation with its events and computes the
following figures in Python:
\begin{itemize}
  \item totals of donations, completed, active (non-terminal) and expired
    donations, organisations and couriers; and the sum of the quantities of
    completed donations (summed across units);
  \item \textbf{median time-to-claim}: minutes from a donation's creation to
    its first \code{ACCEPTED} event;
  \item \textbf{median handover time}: minutes from the first \code{ACCEPTED}
    event to the \code{DELIVERED} event;
  \item \textbf{rescue rate}: completed donations whose \code{COMPLETED} event
    is no later than the pickup deadline, as a percentage of donations that
    completed or expired;
  \item \textbf{expiry-loss rate}: expired donations as a percentage of those
    that completed or expired.
\end{itemize}
Any signed-in role may call the endpoint; only the administrator screens
display it. The donor, organisation and courier impact pages compute figures
from the account's own donations instead (D-32).

On the create-donation screen, the pickup deadline is entered as a clock time.
\code{lib/time.ts} converts it to an absolute instant, rolling a time already
passed today forward to tomorrow. The pickup pin is filled from the browser's
geolocation (\emph{Use my location}) or typed as latitude and longitude. The
screen also resizes a chosen photograph in the browser before upload, because the server caps image data at 256\,KiB and a typical phone
photograph is several megabytes. According to the project's task record, a
4032$\times$3024 photograph was reduced from about 3.46 million data-URL characters
to about 221 thousand in a browser measurement. That figure is quoted from the
record, not re-measured for this report. The phone-layout screens under
