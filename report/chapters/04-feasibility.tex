\chapter{Feasibility Report}
\label{ch:feasibility}

A feasibility study asks whether a system can be built and used under real
technical, operational, economic, schedule and legal
constraints~\cite{sommerville2016,pressman2015}. Much of FoodLink already
exists, so this chapter draws on evidence from the implementation. For each
dimension it separates what is \textbf{implemented}, what is \textbf{feasible
but not implemented}, and what remains \textbf{future work}.

\section{Technical Feasibility}
\label{sec:feas-technical}

The stack (Table~\ref{tab:stack}) consists of mature, well-documented
open-source components, and the project needed no experimental technology and
no external service. The strongest evidence of feasibility is that the complete
workflow runs today and passes 651 automated tests.

On the \textbf{frontend and backend}, four React portals and 27 stateless REST
routes, whose rules are inspectable data, are implemented. Feasible but not yet
built are portal controls for the API-only operations, routing phone visitors to
\code{/m/*}, a global exception handler, profile bounds, and a scheduled caller
for the expiry sweep, which is already an idempotent endpoint. The
\textbf{database} consists of six tables under Alembic migrations on SQLite,
which needs no database server. PostgreSQL is feasible because all access goes
through SQLAlchemy and the concurrency guards are plain conditional updates.
However, no driver is pinned, the tests have never run on PostgreSQL, and the
guards rely on its default \textsc{read committed} isolation (D-28). SQLite
permits one writer~\cite{sqliteWhenToUse}, which suits a single-process pilot
but not several workers. For \textbf{authentication}, bcrypt, expiring signed
tokens and a fail-closed key are implemented. Token revocation and security
headers are feasible next steps, while email verification and MFA are future
work.

\textbf{Deployment.} No deployment configuration exists, but a single-process
SQLite deployment is feasible now under five constraints. Migrations run at
start-up, which is safe with one process only (D-23). Rate-limit counters live
in process memory (D-27). Behind a proxy, the forwarded client address must be
trusted explicitly. The deployed origin must be added to the CORS allowlist and
the signing key supplied as a secret. Finally, the expiry sweep needs an external
scheduler.

\textbf{Complexity.} The domain is small (six tables, nine states), but the
implementation is not trivial: SQL read scopes, reader-specific disclosure,
race-safe transitions and location privacy. The team delivered it through small,
tested increments, and the remaining work is algorithmically simpler.

\textbf{Assessment:} technically feasible, and already demonstrated for the core
system. The main open risk is the untested production database and deployment
topology.

\section{Operational Feasibility}
\label{sec:feas-operational}

\textbf{Donors} complete a single form with automatic photo resizing, but have
no map picker, push updates or cancel button. \textbf{Organisations} first wait
for verification, a deliberate delay that requires genuine administrator
vetting. After that they accept with one action, confirm receipt on
\emph{Accepted Deliveries} and maintain needs on \emph{Food Requirements \&
Demand Signals}. The serious gap is that no screen sets an organisation's map
coordinates, so a portal-registered organisation is never \emph{suggested} to
donors until its pin is set through the API. \textbf{Couriers} judge runs from a
coarse area, claim one, and record pickup and delivery with one button each.
Availability is advisory, and only the organisation (via the API) or an
administrator can release a claimed run. \textbf{Administrators} verify
organisations, monitor donations, run the sweep and review analytics in the
portal. Managing accounts through the API or command line is workable only for a
small, technically supervised pilot.

Every point of custody keeps a human decision (accept, claim, confirm), and
nothing is assigned automatically~\cite{foodlinkProposal}. The main risk is
timeliness without notifications.

\textbf{Assessment:} operationally feasible for a supervised campus pilot.
Unsupervised use needs notifications, a map-pin field and the missing controls.

\section{Economic Feasibility}
\label{sec:feas-economic}

No hosting provider or pilot scale has been chosen, so no monetary figures are
given. Development cost is the four-member team's time within the course. All
software dependencies are open source with no licence fees, and the only
services used are a Git hosting platform with CI and an online LaTeX editor.
There is no infrastructure cost today, since nothing is deployed and the backend
calls no paid APIs. A pilot would need a small application server and, later, a
managed database. Notifications, photo storage and routing would add usage-based
charges, which have not been estimated. SQLite, straight-line distance and
browser-side photo resizing were chosen partly because they keep costs down. On
the benefit side, rescue rate and expiry-loss rate become measurable once the
system is used; no benefit figures are claimed.

\textbf{Assessment:} economically feasible at course and pilot scale.

\section{Schedule Feasibility}
\label{sec:feas-schedule}

The course requires a proposal in week~4, this report in week~7 and a final
report in week~17~\cite{ucs503Project}. The first commit is dated 29 July 2026,
and 85 commits existed by 13 September 2026 (\texttt{e588b35}). The lifecycle,
matching, requirements and authentication are complete for a pilot, and the web
portals cover the core flows. Phone layouts and frontend test coverage are
partial, and deployment and the pilot have not started. The remaining course
work, in priority order, is:
\begin{enumerate*}[label=(\arabic*)]
  \item the P2 items (exception handler, profile bounds, deep link, frontend
    tests and mobile residue);
  \item portal controls for the API-only operations, plus a map-pin field;
  \item a deployment with a scheduled sweep;
  \item a short pilot.
\end{enumerate*}
Notifications, road distances, photo storage and weight tuning lie beyond the
course.

\textbf{Assessment:} schedule-feasible. The core was delivered by mid-term, and
the main risk is recruiting real participants for a pilot.

\section{Legal, Security and Privacy Feasibility}
\label{sec:feas-legal}

FoodLink stores names, emails, phone numbers, organisation addresses, donors'
pickup locations, photos and activity history. Any deployment in India would
have to comply with the Digital Personal Data Protection Act,
2023~\cite{dpdpAct2023}; this report gives no legal opinion.

Authentication, four-layer authorization, verification and location-disclosure
controls are implemented (Section~\ref{sec:module-auth}). Session revocation and
MFA are missing. Descriptions, photos and notes are not scoped, so an address
typed into a description would be exposed. Before public use, FoodLink needs a
privacy notice and consent at sign-up; ways to obtain, correct or delete
personal data (accounts can currently only be deactivated); a retention policy;
and protected hosting and backups. On food safety, the platform records storage
type, preparation time and deadline but does not certify food, and inspection
rests with the recipient~\cite{foodlinkProposal}. Terms of use stating this, and
a review of food-safety obligations, are still needed.

\textbf{Assessment:} suitable for a supervised pilot with informed participants.
Public operation requires the privacy, consent, data-rights and terms measures
above.
