\chapter{Results and Evaluation}
\label{ch:results}

FoodLink has not been deployed or used by real donors, organisations or
couriers. Its mid-term evaluation therefore rests on \emph{verification}:
checking that the behaviour matches the requirements, and that the security,
privacy and integrity properties hold under adversarial and concurrent use.

\section{Testing Methodology}
\label{sec:testing}

Every audit fix arrived with regression tests that fail without the
fix~\cite{pressman2015}. \textbf{Unit tests} exercise the backend matcher's
formulas, gates, unit handling, blurring and tie-break directly, together with
configuration and the rate limiter. On the frontend, Vitest covers the library
modules for adapters, time, location display, impact, the HTTP client and photo
resizing.

\textbf{Integration tests} make up most of the backend suite. They drive the
full HTTP stack against a fresh in-memory SQLite database with no mocks (D-17),
and try every role against every scoped read and transition. Concurrency tests
interleave two real transactions on a file database to reproduce, and then
refuse, lost updates. Migration tests compare a database built from the Alembic
history with the models, and frontend component tests check both what screens
show and what they must not show. \textbf{Performance testing} has not been
performed, so no load, stress or response-time data exist. \textbf{User
testing} has not been conducted either; the proposal's
pilot~\cite{foodlinkProposal} remains future work.

The 27 backend test files are grouped by the property they protect: accounts
and configuration, input validation, read and disclosure scopes, lifecycle and
concurrency, and matching and location privacy. On every push, a GitHub Actions
workflow runs two jobs. The backend job runs \code{pytest}, then
\code{alembic upgrade head} and \code{alembic check}, to catch models committed
without a migration. The frontend job runs \code{npm test} and
\code{npm run build}, which includes the TypeScript compiler. CI deploys nothing
and holds no secrets (D-25).

The evidence has gaps. The production build was not re-run for this report,
because it writes into the repository; CI runs it on every push. No
response-time or throughput figures exist. The proposal's outcome
metrics~\cite{foodlinkProposal} are computed by \code{GET /api/metrics} but have
no real data yet: median time-to-claim (target $\leq$\,45 minutes), rescue rate
(target $\geq$\,80\%), expiry-loss rate (which also depends on the manual sweep
having run) and handover time. User-clarity ratings are not instrumented, and
service availability cannot be measured while nothing is deployed.

\section{Analysis}
\label{sec:analysis}

\textbf{Objectives.} Objectives 1--5 and 7 are met. Objective~6 exists only as
instrumentation, and Objective~8 (deployment and pilot) has not started.

\textbf{Beyond the proposal.} Ranking and requirements, planned as later
deliverables, are both implemented. So are properties the proposal did not name:
reader-specific disclosure, race-safe transitions, abuse limits, and reliability
accounting that cancellations cannot distort.

\textbf{Challenges.} The hardest problems appeared only under adversarial or
concurrent use. Each was reproduced against the running system, fixed with the
smallest change that made the property hold everywhere, and recorded as a
decision (Table~\ref{tab:challenges}). None needed a schema change.

\subsection{Current Limitations}
\label{sec:limitations}

\begin{enumerate}
  \item \textbf{Not deployed, no real-user pilot:} there is no deployment
    configuration, PostgreSQL is untested, and no outcome or performance data
    exist.
  \item \textbf{Missing portal controls:} cancellation, release and account
    management work only through the API. No screen sets an organisation's map
    coordinates, so an organisation created through the portal or by an
    administrator cannot be ranked until its pin is set through
    \code{PATCH /api/recipients/me}. In practice, only organisations with
    coordinates (such as the seeded ones) appear in rankings.
  \item \textbf{No notifications or maps:} users must open the portal to see
    changes. Distances are straight-line with a flat 20\,km/h travel estimate,
    and pins come from geolocation or typed coordinates.
  \item \textbf{Manual expiry:} the sweep's write is unguarded, and an
    administrator's \code{ACCEPTED}\,$\to$\,\code{EXPIRED} leaves the acceptance
    counted.
  \item \textbf{Sessions:} no revocation, refresh token, MFA or CSP, and
    rate-limit counters are per process.
  \item \textbf{Heuristic weights:} the matching weights and reliability prior are
    judgement, not tuned on data.
  \item \textbf{Scale:} photos are stored inline, every write reloads up to 500
    donations, ranking and metrics run in Python, and SQLite allows one writer.
  \item \textbf{Validation gaps:} profile text is unbounded, and unexpected errors
    return an empty 500 response.
  \item \textbf{Mobile residue:} the phone camera screen simulates a photo read
    with a fixed address, one mobile profile shows a hard-coded email, and the
    \code{/ngo/available/:id} deep link does not select a donation.
  \item \textbf{Metric caveat:} the completed-meals total adds quantities across
    units.
\end{enumerate}
