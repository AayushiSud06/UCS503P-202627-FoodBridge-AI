# Migrations

Alembic owns FoodLink's database schema. Nothing calls
`Base.metadata.create_all` any more except the test suite, which builds
throwaway in-memory databases from the models directly.

The database URL is **not** in `alembic.ini` — `env.py` reads it from
`foodlink.config.Settings`, so `DATABASE_URL` points the migrations and the
application at the same place by construction. Building `Settings` also applies
the signing-key rule, so `FOODLINK_SECRET_KEY` (or
`FOODLINK_DEV_INSECURE_SECRET=1`) must be set to run any Alembic command, the
same as for `uvicorn` and `python -m foodlink.cli`.

Run commands from `code/`, or from anywhere with `-c code/alembic.ini`.

## Everyday use

```shell
alembic current                       # what revision this database is at
alembic history                       # the revision chain
alembic upgrade head                  # apply anything outstanding
alembic revision --autogenerate -m "add donation notes column"
alembic downgrade -1                  # step back one revision
```

Starting the API (or the CLI, or `python -m foodlink.seed`) runs
`upgrade head` in process, so a fresh database is created from the migration
history and an out-of-date one is caught up automatically. Running `alembic
upgrade head` by hand is only needed when the schema must move without starting
the app.

**Always read an autogenerated revision before committing it.** Autogenerate
detects most things but not all — a column rename comes out as a drop plus an
add, which loses the data in it.

## Bringing an existing database under control

A `foodlink.db` created before migrations existed has all six tables and no
`alembic_version` row. Do **not** run `upgrade head` against it: the initial
revision starts with `CREATE TABLE users` and would fail.

Baseline it instead. This writes one row recording where it already is, and
changes no table and no data:

```shell
alembic -c code/alembic.ini stamp head
```

Confirm with `alembic current`, which should print the head revision. Later
revisions then apply to it normally.

Startup detects this state and says the same thing rather than guessing — see
`foodlink/migrate.py`.

## SQLite

Revisions are generated with `render_as_batch`, so ALTERs are emitted as
SQLite's copy-and-move table rewrite. That is what makes column changes
possible at all on SQLite, and it is a no-op on Postgres.
